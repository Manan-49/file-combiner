Project context guide

How to combine project files for AI coding

Turn a project folder into a focused context file that an AI coding assistant can understand. Keep the files that explain the task, remove repository noise, preserve paths, and leave room for the model's response.

Published August 31, 2026 · 8 min read

When you ask an AI assistant to debug or modify a project, the hard part is often giving it the right project context. A project may contain source code, tests, configuration, documentation, generated assets, dependencies, caches, and local environment files. Sending everything is rarely the best approach.

A better workflow is to combine the relevant project files into one structured document. The result can be pasted or uploaded as context for a coding task while retaining the original file paths and clear boundaries between files.

What project files should you combine?

Start from the task rather than from the directory tree. If you are debugging an API endpoint, the route, handler, service layer, types, relevant configuration, and failing tests may be enough. If you are refactoring a UI component, include the component, its direct dependencies, related hooks or state, styles, types, and tests.

Useful project context commonly includes:

  • The application entry point or relevant route.
  • Source files that implement the behavior being discussed.
  • Direct dependencies and shared types that affect the behavior.
  • Tests that reproduce the bug or describe expected behavior.
  • Relevant configuration files and a concise README when they explain runtime or architecture.
  • A file tree or path headers so the AI can understand where each file belongs.

Exclude project noise before combining

A project folder can contain far more data than an AI needs. Dependency directories, Git metadata, build output, caches, coverage reports, logs, and generated bundles add tokens without necessarily adding useful reasoning context.

For a typical web project, consider excluding node_modules, .git, .next, dist, build, coverage, cache directories, and large generated assets. Keep a lockfile only when dependency versions are relevant to the question.

Important: environment files and credentials should not be included merely because they are part of the project. Treat .env, private keys, tokens, passwords, and deployment secrets as sensitive data and review the final output before sending it anywhere.

Why combine a project into one file?

A single structured document gives the model a compact representation of the selected project context. It also makes the boundary between files explicit, which is useful when several modules contain similarly named functions or components.

The goal is not to flatten a repository blindly. The goal is to create a reproducible snapshot of the files needed for one task. If the model later asks for a missing module, add that module and regenerate the context rather than sending the entire repository.

Choose Markdown, XML, or plain text

Markdown

Markdown is a practical default for ChatGPT, Claude, Gemini, and many code-review workflows. File paths can be headings and source can remain in fenced blocks, making the combined document easy for both people and models to scan.

XML

XML can make structure explicit with tags around each file. It is useful when you want a strong distinction between metadata, file paths, and source content.

Plain text

Plain text has the least formatting overhead. It works well when you want a lightweight context file, provided that every file still has an unmistakable path and separator.

Preparing context for AI coding tools

The same combined project context can be useful across different AI coding workflows. For ChatGPT, Claude, or Gemini, provide a short task description followed by the relevant context. For IDE assistants, use the combined document when the tool's normal project indexing or file references cannot provide the required context.

Be explicit about what the model should do. Ask for a diagnosis, patch plan, code changes, tests, or documentation rather than simply saying “understand this project.” Also tell the model not to assume files that were not supplied.

Example task: “Review the selected project files and find why the authenticated API request returns stale data after an update. Trace the data flow, identify the most likely cause, propose the smallest fix, and list tests that verify it. Do not assume implementation details from files that are not included.”

Keep enough room for the AI response

The context window is shared by your instructions, project material, conversation history, tool output, and the model's response. A project that technically fits the advertised limit can still leave too little room for useful reasoning or generated code.

Use a token estimate as a planning aid and leave a safety margin. If the combined project is too large, remove distant or unrelated modules first. Then remove generated output and documentation that does not affect the task. Keep the smallest coherent set that lets the model trace the behavior without guessing.

A practical project-to-prompt workflow

  1. Define the task. Write one sentence describing the bug, feature, review, or refactor.
  2. Select the project folder. Start broad enough to find the relevant code, then narrow the selection.
  3. Apply exclusions. Remove dependencies, build artifacts, caches, Git metadata, logs, and sensitive files.
  4. Check the file list. Make sure the implementation, consumers, contracts, and tests are represented.
  5. Choose an output format. Markdown is a good default; XML or plain text may fit specialized workflows better.
  6. Check the context estimate. Leave room for instructions and the AI's answer.
  7. Review the generated document. Remove secrets and unrelated proprietary information before sharing.
  8. Give the AI a precise request. State the expected output and tell it not to invent missing files.

Review privacy before sending project context

A project context file can contain more information than expected. Search the output for credentials, internal endpoints, customer data, private URLs, certificates, and proprietary configuration. Automated secret masking can help, but it should be treated as a safeguard rather than proof that the output is safe.

For sensitive projects, a browser-local workflow is useful because the source files can be processed without uploading them to a file-combining server. You should still follow your organization's policies and the destination AI provider's data-handling requirements.

FAQ

Combining project files for AI

Should I combine my entire project for an AI prompt?

Usually no. Start with the files that implement the requested behavior, their direct dependencies, relevant configuration, and tests. Add more files when they resolve a specific uncertainty.

Can I combine project files for ChatGPT, Claude, or Gemini?

Yes. A structured Markdown, XML, or plain-text context file can be used in many AI coding workflows. Check the destination service's current file and context limits before sharing a large project.

What should I exclude from a project before sharing it with AI?

Common exclusions include dependency directories, Git metadata, build output, caches, coverage, large logs, generated bundles, and secrets. Keep a file only when it materially helps answer the task.

Is combining project files the same as converting a codebase to a prompt?

They are closely related workflows. Combining files creates the structured source context; the final prompt adds the task, constraints, and expected output that tell the AI what to do with that context.
